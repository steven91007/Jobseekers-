# 0e83df7 Add Discord bot that pushes new LinkedIn jobs daily

## Summary
Adds a Discord bot (python -m bot) that stores per-channel job subscriptions in SQLite and pushes only previously unseen LinkedIn jobs once a day. Slash commands under /jobs handle subscribe, list, preview, run, status, toggle and remove. Scheduling is a 5-minute ticker plus a UNIQUE run_marker claim so the daily cycle runs exactly once and catches up after sleep or restart. Scrapes run in a worker thread, subscriptions are processed serially with jittered gaps, a circuit breaker aborts after two consecutive blocks, jobs are marked seen only after a successful send, and alerts fire only on healthy-to-broken transitions. An offline test suite with fake Discord objects covers the push logic, and a Chinese README documents setup and design.

## Why
Turn the interactive CLI into an unattended daily notifier. The commit message explains each reliability decision: tasks.loop timers lose the day if the machine sleeps, wait_for cannot cancel threads, tasks.loop swallows exceptions, and undeduped alerts would spam a 5-minute ticker.

## Risks
Guest-API scraping from a fixed IP can still get blocked; the breaker limits but does not prevent that. The first run of a new subscription posts nothing (baseline only), which users may mistake for a failure. The seen_jobs retention floor of 60 days is enforced in config. Global slash commands can take up to an hour to appear.

## Commit message
```text
Add Discord bot that pushes new LinkedIn jobs daily

Subscriptions are managed with /jobs slash commands and stored in SQLite;
each day the bot scrapes each subscription and posts only job ids it has not
posted before, per subscription.

Scheduling is a 5-minute ticker plus a run_marker row, not tasks.loop(time=).
A once-a-day timer fires exactly once and silently loses the day if the
machine was asleep at push time, which on a Windows desktop it will be. The
UNIQUE constraint on run_marker.run_date is what makes the cycle exactly-once
across sleeps, restarts and gateway reconnects, and it catches up on wake.

Reliability decisions worth knowing:
- Scrapes run via asyncio.to_thread; blocking the loop stalls the heartbeat
  and gets the bot disconnected. The real budget is the deadline inside the
  sync function, because wait_for cannot cancel a thread -- it would leave it
  hammering LinkedIn while a retry starts a second one.
- Jobs are marked seen only after the send succeeds, so a transient Discord
  failure cannot swallow them permanently. Jobs past the per-push cap are
  marked seen deliberately, or they would re-queue forever.
- Subscriptions are scraped strictly serially with jittered gaps, and two
  consecutive blocks abort the rest of the cycle.
- tasks.loop swallows exceptions and stops permanently while the bot stays
  online looking healthy, so there is a guarded body plus an @error handler.
- Alerts fire only on healthy->broken transitions; on a 5-minute ticker an
  un-deduped alert would DM hundreds of times. Recovery is announced too.
- A cycle where >=80% of subscriptions return zero rows is reported once as a
  platform failure rather than N coincidences.

Uses Intents.default() rather than Intents.none(): still entirely
non-privileged, but keeps the guilds intent that get_channel() and guild.me
depend on.

tests/test_pusher.py covers the push logic offline against fake Discord
objects -- no token, no network. It caught a real bug: a subscription that
failed on its first run took the seeding path on recovery, which returned
before the alert was cleared, leaving it flagged broken forever.
```
